## 1. 任务与起点

`coworker/server/app.py` 曾把整个 HTTP/WS 表面装在一个 `create_app` 闭包里：3184 行、
**217 条路由**（216 条常驻 + 1 条 `COWORKER_DEBUG_INJECT` 门控），处理器以闭包方式使用
`manager` / `api_token`。P2 的目标是按域拆成 `APIRouter`，让「一个域一个模块」可发现、
`create_app` 变成一张目录，同时**不改变 HTTP 表面**。

方案 A = 先把当前表面固化成基线，再逐域抽取，每次抽取都是纯搬移。

## 2. 方法：守卫先行 + 纯搬移

三条约定贯穿全部提交：

1. **基线先行。** 抽取前先把「有序的 (方法, 路径, 端点名) 列表」固化成快照。顺序是行为：
   FastAPI 按注册顺序匹配，`/v1/personas/catalog` 早于 `/v1/personas/{persona_id}` 才不会被
   吞掉。
2. **工厂注入而非依赖注入。** 每个模块暴露 `build_*_router(manager[, api_token])`，处理器体
   逐字搬移、仍以闭包/参数方式使用 `manager"`，因此没有一处函数签名改动，审查 diff 时
   只需要看「有没有偷偷改逻辑」。
3. **一次提交一次全量。** 每个提交都在其后的代码树上跑一次全量测试并记录数字。

### 第 8 轮 · WebSocket turn 生命周期（`0479ef6`，0 条路由）

- 新增 `server/ws_turns.py`：`TurnRunner` 持有 `claim` / `run` / `resolve_pending` /

`broadcast ok` → 反查 `ws.py`，`register_session_client` 缺失、`unregister_session_client` 还在。

### 第 9 轮 · 入站帧类型矩阵（`f640160`，测试）

表驱动分发的前置条件：先把现有 `if/elif` 的**决策**钉死。`tests/test_ws_frames.py` 共 28 例，
只断言分发决策（是否被拒、拒绝文案），不重复深度效果。

写这个测试时踩了个坑：第一版直接 `receive_json()` 读回复，结果**挂死**——被接受的帧大多
不回复（socket 只在 turn 运行或提示被解决时说话）。改成**探针帧**：每例先发候选帧，再发
必然被拒的 `{"type": "__probe__"}`，探针拒绝之前收到的内容就属于候选帧。这样「静默接受」
与「根本没被处理」才区分得开，不靠 sleep。

证据：28 passed（2:18）；ruff 干净。

### 第 10 轮 · 表驱动分发（`785329e`，0 条路由）

接收循环的 `if/elif` 链换成查表（`FRAME_HANDLERS`），信封校验（JSON / 限流 / 对象 / type 类型）
留在原地：它们判的是帧本身，与帧类型无关。十二个处理器下沉为模块级函数，统一接收窄上下文
`_SessionSocket`（manager / engine / turns / session_id / workspace / reject / send）。

两个设计点写进了注释：`team_response` 与 `items_response` 共用 `_on_team_response`（同一裁决
形状、同一个 Inbox plan 条目）；附件整段校验抽成纯函数 `_ingress_problem`（这些上限是 socket
防止把超大帧缓冲成模型内容的全部防线，值得脱机读和测）。检查顺序与每条文案逐字未改。

`routes/ws.py` 505 → 574 行——行数是这次唯一变差的指标：原来的链是嵌套的，现在处理器是平
的、循环只剩五行，新增一个帧类型 = 表里一行 + 矩阵里一例。

证据：帧矩阵 28 + `test_server.py` 49 = **77 passed（6:36）**；ruff 干净。

## 5. 缺陷账本

本轮所有缺陷都是**搬移过程**引入的，没有一处是原有逻辑错误。记录在此，因为教训比结论有用。

| # | 问题 | 发现方式 | 处理 |
|---|---|---|---|
| 1 | PowerShell 往返覆写 `app.py`，UTF-8 中文变乱码 → f-string 语法错误 | 立即 `ruff`/导入报错 | `git checkout` 回滚，改用 Python 脚本按 `encoding="utf-8"` 重放 |
| 2 | 拼接重复一行 `# -- connectors` 注释 | 阅读 diff | 后续提交一并清理 |
| 3 | 模块写好但未 include（`observability` / `attachments_messaging`） | 统计装饰器数 88 vs 已接线 75 | 当轮接线；第 7 轮固化为守卫 |
| 4 | `_request` → `request` 全局替换误伤 `tool_request` → `toolrequest` | 23 个用例 `AttributeError` | 修正方法名；此类替换必须带词边界 |
| 5 | `run.py` 仍 `from .app import _WS_MAX_FRAME_BYTES` | `test_frontend_spa` 收集失败 | 改从 `routes.ws` 导入，测试同步 |
| 6 | `textwrap.dedent` 处理 800 行块导致缩进错位 + `return app` 被搬走 | `ruff` F821 + 语法错误 | 回滚，改按行号切片并保留原缩进 |
| 7 | 切割区间吞掉 `register_session_client` 与 Auto-Approve 提示块 → WS 用例挂起 | A/B 回退 + faulthandler + 打点 | 按 HEAD 原文恢复 |
| 8 | 同一区间吞掉 `inbound_times = deque()` | `ruff` F821 ×5 | 补回 |

三条可复用的操作规则：

1. 搬移代码用**函数/区段边界**定位，不要用关键字窗口；切割后立刻对比「符号清单前后差异」。
2. 用词边界替换标识符（`\bname\b`），不要裸 `str.replace`。
3. 不要用 shell 的读写往返处理含非 ASCII 的源码，一律 `encoding="utf-8"` 的脚本或编辑器。

## 10. P3 第 4 项：`except Exception` 收窄

盘点：`coworker/` 下 **247 处** `except Exception` + 1 处 bare。只有 8 处带「故意宽」标记
（`noqa: BLE001` / deliberate / best-effort），9 处会 re-raise。也就是说**全量收窄不是选项**。

分布（前几）：`engine.py` 29、`connectors/email_tools.py` 15、`testing/fake_slack/server.py` 10、
`connectors/browser_automation.py` 8、`connectors/relay_client.py` 8、`connectors/adapters.py` 7、
`automation/scheduler.py` 6、`trajectory.py` 6，其余为长尾。

### 10.1 判断规则

这轮把「窄还是宽」从直觉变成了两条可执行的规则：

| 情形 | 处理 |
|---|---|
| 具体实现的失败面（JSON 解码、`int()`、base64、IMAP/SMTP、httpx、子进程管道） | **收窄**到真实异常类型 |
| 本地序列化 / 本地存储（账本、轨迹、缓存） | **收窄**到 `(OSError, ValueError, TypeError)` |
| Protocol / 回调 / 注册表 / SDK / tick / 流式边界 | **保留宽 + 注释理由** |

第二条规则的理由是这轮反复验证的：在边界处收窄等于把「某个实现失败」升级成「整条链路挂掉」
—— relay 断线不再重连、调度器一次 tick 失败就停摆、工具异常直接崩 turn。

## 11. P3 第 5 项：真实模型矩阵

### 11.1 它是什么

`python -m coworker.eval.matrix`：把录制用例的每一轮用户输入，在「harness × model」的每个
cell 里用**全新引擎**重跑，收集每轮 `model_request` 的 digest / bytes / tools，形成可横向比较的
报告。

- 用例：`--case <dir>`（`messages.jsonl` + `baseline.json`）或 `--session <id>`（本地录制）
- harness：内置 `minimal` / `code` / `creator` / `code-mode`，或任意已装 persona
- cell：(harness, model)，每个 cell 一个引擎 + 临时轨迹账本，互不污染
- 当前用例 `evals/ci-case` 有 2 轮（"list the files in the workspace" / "summarize what you found"）

### 11.2 三种运行方式

| 方式 | 命令 | 用途 |
|---|---|---|
| CI（key 不进本机） | Actions → Eval → Run workflow（`matrix-real`，仅 `workflow_dispatch`） | 真跑，产物 artifact `eval-report-real` |
| 本机 | `.venv\Scripts\python.exe -m coworker.eval.matrix --case … --models …` | 调试、试新 provider |
| 离线 stub | 加 `--stub` | 不联网、不花钱，验接线与基线门禁 |

本机要注意两件事：用 **`.venv` 的解释器**（全局 `python` 里没有 `aisuite`），并把
`COWORKER_STATE_DIR` 指向临时目录（否则污染真实 state）：

```powershell
$env:COWORKER_STATE_DIR = "$PWD\.tmp-verify\eval-state"
.venv\Scripts\python.exe -m coworker.eval.matrix --case evals/ci-case `
  --models "scnet:SCNet-Max,unisound:u2-flash" --harnesses minimal `
  --workspace .tmp-verify/eval-ws --out .tmp-verify/eval-real.json
```

### 11.3 关键参数

| 参数 | 语义 |
|---|---|
| `--stub` | 确定性假 provider，不联网 |
| `--check-baseline` | 与用例基线比，漂移即 **exit 3** |
| `--max-bytes-ratio` | 允许的字节相对偏差（CI 传 `0.10`） |
| `--baseline-file` | 指定基线文件（默认 `case/baseline.json`）；真实模型指向 `real-baseline.json` |
| `--write-baseline` | 用本次 `--stub` 运行重写 `baseline.json`（单 cell） |
| `--auto-approve` | 自动批准工具调用；**默认关** |
| `--max-turns` | 只跑前 N 轮（0 = 全部），快速热身用 |
| `--timeout` | 单轮墙钟上限（默认 180s）；超时记 `timeout` 并停在该 cell |
| `--out` | 报告 JSON 路径 |

`--auto-approve` 默认关是有意的：开了以后引擎会自动批准工具，**被测量的东西变了**（带工具
vs 纯推理）。两种跑法应该各自记基线，不要混。

### 11.4 真实事故：基线对「在不在 git 仓库里」敏感（2026-11-13 修）

先记一段被推翻的结论：`evals/ci-case/baseline.json` 停在 2026-11-07（2734 / 2823 字节），
而本机跑出 3132 / 3221——**两轮同样 +398**，当时判断是「系统提示/harness 清单变长」。那是错的：
`+398` 来自 workspace 落在仓库里，环境块把 git 快照（branch / status / recent commits）
一起写进了载荷。

证据（CI 日志，run #73 的 `gate-stub`）：

```
turn 1: bytes 2693 vs base 3132 (△-439), tool_calls 0/0 [ok]
turn 2: bytes 2782 vs base 3221 (△-439), tool_calls 0/0 [ok]
baseline check: 2 failure(s) (max_bytes_ratio=0.1)
```

两轮同样 −439，且 439/3132 = 14.0% > 10% 容差 → push 触发的门禁恒红。CI 的 workspace 是
`${{ runner.temp }}/eval-ws`（空、非 git），本机那份基线却含 git 快照，所以永远差一大块。

修法两条：

1. 用**仓库外的空目录**重新生成基线（`--workspace $env:TEMP\ow-eval-ws`）→ **2748 / 2837**；
   本地复验 +6 字节、`baseline check: ok`；与 CI 的 2693 / 2782 相差 −55（2.0%），在容差内。
2. CLI 加护栏：`--write-baseline` / `--check-baseline` 时若 workspace 在 git 工作树里，
   `_in_git_worktree` 会打印警告，因为这种基线不可能与 CI 对齐。

旧结论的另一半也要纠正：之前观察到的「连续两次 stub 相差约 81 字节」同样是 `git status`
在变。换成空目录后**字节完全确定**（两次跑都是 2752 / 2841），但 **digest 不同** —— 载荷里
有一个定长却逐次变化的字段（本次未深挖，疑为会话 id）。所以门禁只能以字节为准，digest 只作
参考；容差保留 10% 是为了吸收路径与平台字符串（`C:\Users\…\Temp\…` vs `/home/runner/…`）。

### 11.5 用 SCNet / 云知声替代 OpenAI / Anthropic

两家都提供 OpenAI 兼容接口，因此走已有 `_compat` 描述符路径（`be13669`），不需要新客户端，
key 也不会回退到 `OPENAI_API_KEY`：

| provider | 端点（预填、可改） | 模型串 | 环境变量 |
|---|---|---|---|
| `scnet` | `https://api.scnet.cn/api/llm/v1` | `scnet:SCNet-Max` | `SCNET_API_KEY` |
| `unisound` | `https://maas-api.unisound.com/v1` | `unisound:u2-flash` | `UNISOUND_API_KEY` |

key 的三条配置路径：

1. **GUI**：Settings ▸ Models → 对应卡片 → 填 key（端点已预填），存进 `provider:<name>` profile；
2. **进程环境变量**：`$env:SCNET_API_KEY="…"`（当前会话）或
   `[Environment]::SetEnvironmentVariable(...,"User")`（持久，需重启客户端）；
3. **`.env` + `${VAR}`**：state 目录下的 `.env` **只参与 profile 里 `${VAR}` 的解析，不会注入
   `os.environ`**，所以只有 `.env` 没有带 `${VAR}` 的 profile 是不生效的。

CI：`.github/workflows/eval.yml` 的 `matrix-real` 已注入五个 key（`530d32d`），缺 secret 时展开成
空字符串，builder 会报 `No … API key configured`（厂商名入文案），job 快速失败而不是跑空 cell。

### 11.6 门禁怎么开（2026-11-13 已开）

`evals/ci-case/real-baseline.json` 原来只有 **1 个 cell**（`deepseek:deepseek-v4.1` × `minimal`，
2026-11-07）。2026-11-13 用 SCNet / 云知声重跑后换成 **2 个 cell**（见 §11.8），2026-11-14 又把
11-07 的 deepseek cell 合回来，现在是 **3 个模型**（见 §11.9），并补上了「按 model 取基线」的
能力——否则拿 stub 基线（3132/3221 字节）去卡 `SCNet-Max`（9109）必然失败。

`--check-baseline` 的解析规则（`_resolve_cell_baseline`）：

- 基线是**扁平** `turns` 列表（stub 黄金用例）→ 全体 cell 对同一份；
- 基线带 **`cells`** 列表（真实模型报告）→ 按 `(harness, model)` 各比各的；基线里没有的模型
  判 `missing_cell` 失败，**不会静默跳过**。

CI 侧 `eval.yml` 新增 `baseline_file` 输入（默认 `real-baseline.json`）：文件存在则传
`--baseline-file`，不存在且 `check_baseline=1` 时直接报错退出，提示先跑一次 `check_baseline=0`
把报告存成基线。

还有一处更要紧的发现：**`deepseek-v4.1` 已经不在 provider 目录里**。`COMPAT_MODELS["deepseek"]`

`providers/matrix.py` 的上下文窗口表也只有这两个。也就是说这一格**永远不可能被重跑复现**，

所以「三模型」在刷新之前只成立一半：SCNet / 云知声是当前基线的真凭实据，deepseek 是待补记录。
